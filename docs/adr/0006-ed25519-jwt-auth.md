# 6. Ed25519 JWT auth with dual-slot JWKS

Date: 2026-07-09

## Status

Accepted

## Context

TravelAI services must verify user tokens without sharing HMAC secrets. Production
rules require asymmetric JWT with published JWKS and refresh rotation.

## Decision

- `identity` issues access tokens signed with **Ed25519 (EdDSA)**.
- Public keys published at `GET /.well-known/jwks.json` with **two slots**:
  `primary` (sign new tokens) and `secondary` (verify during rotation).
- Missing env PEMs generate ephemeral dual keys in development only.
- Refresh tokens are opaque random 32-byte values, stored as SHA-256 hashes,
  rotated on each `/v1/auth/refresh`.
- Redis sliding counters rate-limit login; account lockout after N failures.

`api` and `ai` verify bearer tokens via remote JWKS (`createRemoteJWKSet`).

## Consequences

### Positive

- No shared HS256 secret across services
- Rotation without downtime (dual slot)

### Negative

- Identity is a hard dependency for authenticated paths

## Alternatives considered

- HS256 shared secret — rejected for production
- Session cookies only — harder for multi-service SPA
